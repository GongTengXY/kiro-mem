## 0. 一页结论

**15 个候选 arm 在安全过滤（G1 ∧ G2 ∧ G3）阶段全部被淘汰，本轮没有安全 arm。**
按判据 §8 第 4 步与 §9 第 9 条，结论是"本轮不通过"——不下调门槛、不删保护线中的任何一类、
不放宽 G2 的 2、不加密网格刻度再扫一遍。

| 门 | 结果 |
| --- | --- |
| **G1 排序污染门（主门）** | **15/15 失败。** 最好一格仍有 **58 次**污染（基线 73 次），且污染下降伴随 `primary_gold` 缺席从 11 条升到 19 条 |
| **G2 容量门** | **15/15 失败。** 超限条数 38 → 29 → 17 → **9**（随 r 单调下降但不归零），最坏 `distinctContent` 3 |
| **G3 标记门** | **16/16 通过。** `match_source` 机械重算 0 不一致，semantic-only 最大 2 |
| **G4 非回退线** | r = 0 的四个 arm 通过（与基线同页），**r > 0 的 12 个全部回退** |
| **召回保护线** | **16/16 通过**，五类的 hit@5 与 MRR 与基线**完全相同** |
| **性能资格门** | **16/16 通过**。基线 p95 = 199.06ms < 300ms，走绝对判定 |
| **S5–S9 自证** | **16/16 全过**（含 S6 恒等锚点 120/120、S7b 差集逐 query 为 0） |

淘汰原因分布：`{ G1: 15, G2: 15, G4: 12 }`。

**一句话机制**：V1 的滑窗覆盖度能把负例的页面压小（G2 超限 38 → 9），
但压不到 cap 要求的 2，而且**同一个动作同时压掉了正例**——G1 的污染计数没有归零，
只是把一部分"污染"换成了"真答案根本不在页面上"。

## 2. G1：污染没有归零，代价是真答案缺席

判据 §6.1 要求两个数分开报，并预先点明了那个可被利用的退化解。实测正是它：

| arm | `pollutionCount` | 涉及 query | `actualDisplacement`（相对基线） | `primaryAbsent` | 正例 hit@5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `r0-d1.00`（基线） | 73 | 30 | 0 | 11 | 0.813 |
| `r0.2-d1.00` | 58 | 23 | 0 | **17** | 0.738 |
| `r0.3-d0.03` | 59 | 24 | **1** | **19** | 0.713 |

三件事必须一起读：

1. **`pollutionCount` 从 73 降到 58/59 不是"污染被治好了"。** 同期 `primaryAbsent` 从 11 升到 19：
   多出来的 8 条 query 的 `primary_gold` 直接掉出页面，而判据 §6.1 规定这种情况**记 0**。
   换句话说，G1 读数变好的一部分来自"没有真答案可被压过"。
2. **`actualDisplacement` 只有 0–1**。相对基线的反事实位移几乎不存在——**不得把 58 次
   描述成 58 次实际位移**（判据 §6.1 的口径纪律，P3 的 `35 次` 同一条）。
3. **`r = 0.3` 的污染（59）比 `r = 0.2`（58）略高。** 方向不单调，说明继续收紧覆盖度
   不会把 G1 推向 0。

基线的 73 次与 P3 记载的 35 次**不可比**：不同校准集、不同装置、不同 query 集，
本轮是新的 80 条正例并集。

## 3. G2：分组读数指出了 V1 的失效边界

Codex 验收第 5 项要求的分组（口径与基线条数在 `f2-freeze-r3.json` 里预登记，先写后跑）
给出了本轮信息量最大的一张表：

| arm | 超限总数 | 修补过的 26 条 | 未修补的 14 条 | 最坏 `distinctContent` |
| --- | ---: | ---: | ---: | ---: |
| `r0-d1.00`（基线） | 38/40 | 25/26 | 13/14 | 10 |
| `r0.2-d1.00` | 17/40 | 16/26 | 1/14 | 10 |
| `r0.3-d0.03` | **9/40** | **9/26** | **0/14** | 3 |

**`r = 0.3` 时未修补的 14 条全部达标，超限的 9 条全部来自修补过的 26 条。**

这不是巧合，而是修补的定义决定的：r2 那轮按裁定把 38 条 query 的锚点换成了
**语料里逐字存在、实测 df ≥ 1** 的短语（`f1-criteria-r4.md` §15）。
于是修补过的负例拥有**真实**的词面锚点，而未修补的那批锚点更弱。
**覆盖度门槛挡得住弱锚点，挡不住真锚点**——而真锚点才是生产里的常态。

按 ftsCount 档看（`r0.3-d0.03`）：

| 档 | 修补 | 未修补 |
| --- | ---: | ---: |
| `1` | 1/3 | 0/1 |
| `2-9` | 4/14 | 0/9 |
| `10-99` | 0/0 | 0/0 |
| `100-999` | 1/5 | 0/3 |
| `≥1000` | **3/4** | 0/1 |

`ftsCount ≥ 1000` 的负例里 3/4 超限——锚点命中上千行时，覆盖度比例几乎必然被满足。

按类别看（`r0.3-d0.03`）：`false-premise` 2/15、`same-word-other-thing` 4/15、
`stale-state-confusion` 3/10。

## 4. 三个预登记预测的逐条验证

判据 §11 写下这三条的唯一目的是"跑完之后没人能声称它们是事后解释"。逐条对照：

**预测一（G2 在"同词不同事"15 条上最可能不通过）——方向成立，但不是唯一失败集。**
`r0.3-d0.03` 的 9 条违规里 `same-word-other-thing` 占 4 条（绝对数最多），
但 `stale-state-confusion` 的比例更高（3/10 = 30% vs 4/15 = 26.7%），
`false-premise` 也仍有 2/15。**失败不集中在单一类别**，因此"覆盖度不是这一类的解"
这句话适用于三类，而不只是同词不同事那一类。

**预测二（精确单元豁免会让混排锚点负例继续进页面）——成立，但它不是主因。**
`r0.3` 的 9 条违规里只有 **3 条（33%）** 带豁免命中，全体 40 条负例的豁免命中合计只有 3。
判据原文写"若 G2 的失败条目里豁免命中数占多数，那么 V1 的形式本身有上限"——
实测是**占少数**，所以结论要反过来说：**失败主要来自覆盖度门槛本身对真实词面锚点无效**，
而不是豁免开的后门。收紧豁免规则不会救 G2。

**预测三（V2 与"历史状态"保护线冲突）——不成立，因为 V2 在本装置几乎没生效。**
`r = 0.3` 族的丢弃单元总数是 0 / 0 / 1 / 7（d = 1.00 / 0.30 / 0.10 / 0.03），
与 F2 的读数一致；`historical-state` 的 hit@5 恒为 1、MRR 恒为 1。
原因已在 F2 登记：60,066 行里 50,000 条英文 filler 一个中文字都没有，
最高频中文功能词的 `df/scope` 也只有 0.0416，低于最小的 `d = 0.10` 档。
**因此本轮对 V2 的结论只有一条：在这个装置上它的效应不可分辨。** 判据 §2.4 第 2 条
明写刻度已冻结、不因这个读数改动，本文照此执行。

## 5. 保护线为什么全过

五类的 hit@5 与 MRR 在所有 16 个 arm 上与基线**完全相同**，这不是判定失效，逐类都有机制：

| 类 | hit@5（基线 → `r0.3-d0.03`） | 机制 |
| --- | --- | --- |
| `short-query` | 0.875 → 0.875 | 走 LIKE 回退分支，V1/V2 结构上不作用于它（判据 §2.1 边界 2） |
| `proper-noun` | 0.75 → 0.75 | 拉丁标识符是精确单元，走 `(a)` 豁免 |
| `path` | 0.625 → 0.625 | 路径被刻意不拆，同上 |
| `number` | 1 → 1 | 数字是精确单元，同上 |
| `historical-state` | 1 → 1（页面缩水 8 条） | 8 条完整中文问句，页面确实缩水了，但它们的 `primary_gold` 都在第 1 位，缩掉的是尾部 |

`historical-state` 那一行是本轮唯一"缩水但不回退"的证据：**页面变小 ≠ 召回变差**，
两者必须分开看，这也是判据要求同时报"页面缩水条数"的原因。

## 8. 本轮不做什么

1. **不加密刻度。** `r0.3` 的最坏 `distinctContent` 是 3，距 cap = 2 只差 1，
   看起来"再收紧一点就能过"。判据 §2.4 第 2 条与 §9 第 12 条禁止在看过读数后增删刻度，
   本文照此执行。而且 §3 的分组读数说明，剩下的 9 条超限全部是**真实锚点**的负例，
   它们的滑窗覆盖度本来就达标——继续抬 `r` 只会更快打掉正例（G4 已在 12 个 arm 上回退）。
2. **不下调 G2 的 2**（判据 §6.2、裁定 Q4）。
3. **不删保护线中的任何一类**，不把"页面缩水"当成回退的豁免理由。
4. **不改判据、不改语义侧参数、不改 `ORDER BY fts.rank, o.id ASC`、不改 K。**
5. **不改生产代码。** `git diff src/` 全程为空——V1/V2 只存在于 benchmark 的注入接缝里
   （`benchmark/fts-round-search.ts` 用代理替换 FTS 腿），因此本轮的"不通过"不需要回滚任何东西。

## 9. 本轮确定了什么（这是结论，不是失败）

plan §2 与判据 §11 都预登记了"本轮可能得出 V1 与 V2 都不足以同时满足门槛与召回保护线"。
实测确认了它，并且比预登记更具体：

1. **词面准入（覆盖度 + df 上限）不能把 FTS 假阳性压到 G2 的容量线以内。**
   最好一格 9/40 超限，而且失败集横跨三个负例类别。
2. **失败的机制不是豁免后门**（只占 33%），而是**真实词面锚点天然满足滑窗覆盖度**。
   因此判据 §11 预测一那句话可以确定下来：**需要的是内容级证据，不是词面计数。**
3. **V1 的收紧与正例召回是同一个旋钮的两端**：G2 超限 38 → 9 的同时，
   正例 hit@5 0.813 → 0.713、`primaryAbsent` 11 → 19、G4 四档全线回退。
4. **V2 在真实规模的混合语料上不可分辨**（丢弃 0–7 个单元）。要测它需要一个中文竞争强度
   高得多的装置，那是另一个装置问题，不是参数问题。
5. **成本不是障碍**：整套机制的新增开销在测量噪声量级内（df 一遍 2.5 ms、腿 58 ms、
   p95 全部 < 300 ms）。**如果将来有一个有效的准入判据，它的实现形状是可负担的。**

## 10. 诚实边界

1. **本轮只测了轨道 B（G2 FTS 准入取证）。** 轨道 A（G1 候选级排序取证）与 Q6 agent 行为取证
   分开进行、分别归因（`gate-shape-ruling.md` §4 第 6 项）。G1 在本轮 15/15 失败这件事
   **不构成轨道 A 的结论**——本轮没有动任何排序变量。
2. **中文 filler 是模板生成的合成语料**，自证的是"分布非退化且未被反向塑造"，
   不是"与真实中文工作区同分布"。V1/V2 的读数外推到真实工作区时受此限制，
   V2 的"不可分辨"尤其如此。
3. **`f2-strata-r2.json` 的四档是冻结前测的**，冻结后复现在 `f2-strata-verify-r3.json`
   （80/80 逐条一致）。G4 用的 band 取自后者。
4. **分段耗时是三段而不是判据 §5.6 写的四段**：「候选生成」与「候选内归因」合并报，
   因为拆开需要在 `fts-round-admission.ts` 内部埋点，而它是 `f2-freeze-r3.json` 的冻结输入。
   性能门只用完整 search p95 判定，合并不影响判定。偏离登记在每份 `perf-*.json` 的
   `boundaries.segmentGranularity`。
5. **分段耗时来自额外调用，不是端到端那次调用的内部埋点**，因此三段之和不构成端到端时间的
   精确分解，只作量级归因（同上，登记在 `boundaries.segmentsAreSeparateCalls`）。
6. **页面 limit = 10 是继承值**，不是本轮选的：G2 的 2 由 Phase 2B 在 limit = 10 下预登记，
   P3 网格同样是 10。F1 判据没有冻结请求级 limit，这是判据缺口，
   已登记在 `f2-freeze-r3.json` 的 `payload.nextPhase.f3.pageLimitInherited`。
7. **门读数阶段缓存 query 向量**（同一段文本的向量恒定，不改变任何返回）；
   **性能阶段用真实 embedder 且每次重复前清空 df 缓存**，所以两类读数各自的口径都成立。
8. **撰写者、实现者与判定者仍是同一人。** 缓解方式与前几轮相同：G1–G4、保护线、性能门、
   S5–S9 与最终选择全部是机械计算，由 `collect-fts-round-f3.ts` 与
   `select-fts-round-arm.ts` 硬失败或硬输出，报告里的每个数字都能从
   `f3-arms/` 的原始读数复算。
