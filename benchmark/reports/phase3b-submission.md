## 2. 主结论

### 2.1 候选池截断的代价：语义腿在规模化后失去大部分触达能力

唯一自变量是 `semanticCandidatePool`。190 条 relevance query（全部有冻结的英文派生值）：

| 指标 | `pool-200`（当前发布） | `pool-full`（全 scope） |
| --- | ---: | ---: |
| **语义腿触达 gold** | 68 / 190（35.8%） | **152 / 190（80.0%）** |
| hit@5 | 36.8% | **65.8%** |
| MRR | 0.361 | **0.617** |
| 可比向量（均值） | 210 | 1989 |

"触达"是比 hit@5 更直接的读数：它区分"打了分但没排上去"与"从未被打分"。pool-200 下有
122 条 query 的正确答案**连一次 cosine 都没算过**。

分层之后，最能说明问题的是 Phase 2 那 72 条：

| 子集 | n | pool-200 触达 / hit@5 | pool-full 触达 / hit@5 |
| --- | ---: | ---: | ---: |
| `phase2`（**全部 ftsCount=0**） | 72 | **0 / 72 · 0.0%** | 43 / 72 · 31.9% |
| `tuned` | 18 | 16 / 18 · 88.9% | 18 / 18 · 100% |
| `heldout` | 18 | 5 / 18 · 27.8% | 18 / 18 · 77.8% |
| `validation` | 20 | 13 / 20 · 65.0% | 20 / 20 · 100% |
| `fusion` | 62 | 34 / 62 · 58.1% | 53 / 62 · 80.6% |

`phase2` 那一行是本轮最干净的证据。那 121 条（本装置里可测 72 条）**全部零关键词命中**，
所以它们只能靠语义腿。目标一旦落在最近 200 条之外，语义腿看不见它，FTS 又没有命中，
于是**结构上不可达**——触达 0/72、hit@5 0.0%。

这句话值得写清楚：**2C 拆掉关键词门换来的那份能力，在 2,000 条语料上被候选池重新关掉了。**
两者不是同一道门，但对用户是同一个结果——"我记得做过这件事，搜不到"。

### 2.2 误召回几乎没有恶化 —— 与 3A 的形状相反

判据 §6.2 要求同时测这一侧，因为候选池扩 10 倍意味着语义腿要给约 9 倍的向量打分：

| 指标 | `pool-200` | `pool-full` | 判定 |
| --- | ---: | ---: | :--: |
| empty 均值（n=86） | 3.56 | 3.80 | 涨 0.24 条/query |
| empty 最坏 | 10 | 10 | 不变 |
| `semanticOnlyMax` | 2 | **2** | ✅ cap 不变量成立 |
| 跨 scope 泄漏 | 0 | **0** | ✅ 硬门成立 |

护栏之所以撑住，是因为 `semanticFloor` 与 `semanticOnlyLimit` 约束的是**分数和条数**，
与候选数量无关。多打 9 倍向量的分，并不等于多 9 倍机会进页。

**但 3.56 这个数字不能与历史的 1.00 / 2 比较。** 本装置里有 1970 条填充，它们也会被 FTS
词面命中，所以这是"2,000 条语料下的误召回水平"，不是同一批 5 条 expected-empty 的连续读数。
历史连续性锁仍然要看 30 条语料上的读数（本轮复跑：均值 1.00 / 最坏 2，未回退）。

### 2.3 向量路径在 50,000 条内不需要 ANN；**完整 search 的 300ms 门槛三档全部未达标**

这一节必须把两个问题分开，因为把它们混在一起是本报告初稿的一处实质错误（见 §2.3.3）。

#### 2.3.1 问题一：全量 brute-force 本身贵不贵 —— 不贵

向量路径单独计时（取 blob + cosine + 排序，**不含** FTS 与 query embedding）：

| 语料规模 | fetch p50/p95 | cosine p50/p95 | **向量路径合计 p95** |
| ---: | ---: | ---: | ---: |
| 2,000 | 1.63 / 6.38ms | 0.71 / 0.79ms | **≈ 7.2ms** |
| 10,000 | 12.17 / 16.82ms | 3.69 / 4.39ms | **≈ 21ms** |
| 50,000 | 68.51 / 95.83ms | 23.45 / 23.78ms | **≈ 120ms** |

成本大致线性（5 倍规模 → 5.7 倍耗时），主要花在读 blob 而不是算 cosine。

**结论：向量路径本身在 50,000 条内无需 ANN。** 方案 §11 "超预算时再评估分页扫描、
SQLite 向量扩展或 ANN"这条触发条件，在向量路径这一侧没有被触发；判据 §2 第 3 条禁止
本轮引入，本轮也没有理由引入。

#### 2.3.2 问题二：完整 search 是否满足 300ms —— **三档全部超限**

判据 §7 登记的门槛是**完整 search p95 < 300ms**，不是某一段的耗时。实测：

| 语料规模 | 完整 search p50 | **p95** | p99 | 门槛 300ms |
| ---: | ---: | ---: | ---: | :--: |
| 2,000（真实文本） | 548.79ms | **1222.97ms** | 1489.56ms | ❌ |
| 10,000（极简文本） | 424.48ms | **629.30ms** | 735.09ms | ❌ |
| 50,000（极简文本） | 3939.56ms | **5985.60ms** | 7192.19ms | ❌ |

**三档全部未达标。** 超限的原因不是候选池、也不是向量路径，而是 §4 那个 `LIMIT ?`
查询计划翻转缺陷——它把 FTS 一段变成 O(语料)，在 2,000 条上就占了总延迟的 99%。

#### 2.3.3 初稿这里写错了，如实留档

本报告初稿在这一节写的是"50,000 条全 scope brute-force 的 p95 约 120ms，在 300ms 预算内"，
并给这一节起名"全量 brute-force 付得起"。

那是一处**实质性的结论错误**，不是措辞问题：120ms 是向量路径的读数，而预登记门槛测的是
完整 search。用一段的耗时去核销一个针对整体的门槛，等于把门槛悄悄换成了一个更容易过的。
这正是判据 §8 "任一项缺失即未通过"要防的事。

正确表述：

> 向量路径本身在 50,000 条内无需 ANN；完整 search 是否满足 300ms，
> **须在修复 FTS 缺陷后重新测量**。

在那次重测拿到读数之前，本项目**没有**任何规模下满足 300ms 的完整 search 证据——
只有 30 条语料上的 12.2ms（见 §4.4），而那个规模测不到该缺陷。

### 2.4 总延迟与候选池无关

| arm | 总 search p50 | p95 | p99 |
| --- | ---: | ---: | ---: |
| `pool-200` | 452ms | 2903ms | 4809ms |
| `pool-full` | 399ms | 2931ms | 5056ms |

两个 arm 几乎相同——**说明总延迟不是池贡献的**。分阶段归因（2,000 条语料）：

| 阶段 | `pool-200` p50/p95 | `pool-full` p50/p95 |
| --- | ---: | ---: |
| query embedding | 1.14 / 1.38ms | 1.73 / 2.36ms |
| **FTS** | **482 / 1251ms** | **477 / 1260ms** |
| 取向量 blob | 0.25 / 0.64ms | 1.63 / 6.38ms |
| cosine + 排序 | 0.09 / 0.12ms | 0.71 / 0.79ms |

FTS 占了 99%。这不是"FTS 本来就慢"，而是 §4 那个缺陷。

## 4. 未预期发现：`LIMIT ?` 让 FTS 查询计划翻转，代价 O(语料)

这是本轮最重要的产出，也是规模装置存在的意义——它测出了一个没人在找的东西。

### 4.1 现象

同一条 SQL，**唯一差别是 LIMIT 用字面量还是绑定参数**，返回行数都是 50：

| 变体 | 耗时 | 返回 |
| --- | ---: | ---: |
| A 完整（JOIN + `ORDER BY fts.rank` + `SELECT o.*`）+ **`LIMIT 50` 字面量** | **0.93ms** | 50 |
| E 同上，但 **`LIMIT ?` 绑定参数（生产实际形式）** | **1506.57ms** | 50 |

1,600 倍。

### 4.2 机制：join 顺序被翻过来

```text
LIMIT 50（字面量）:
  SCAN fts VIRTUAL TABLE INDEX 32:M9              ← 从 FTS 驱动，用它自己的 rank 次序
  SEARCH o USING INTEGER PRIMARY KEY (rowid=?)    ← 按 rowid 精确取回，命中几行取几行

LIMIT ?（生产形式）:
  SEARCH o USING INDEX idx_observations_scope_time (scope_key=? AND turn_stopped_at>?)
                                                  ← 从 observations 驱动：扫 scope 内 90 天全部行
  SCAN fts VIRTUAL TABLE INDEX 32:=M9             ← 对每一行探测 FTS
  USE TEMP B-TREE FOR ORDER BY                    ← 再用临时 B 树排序
```

LIMIT 值在编译期不可知时，SQLite 不再从 FTS 驱动，而是**扫 scope 内时间窗内的全部
Observation，逐行探 FTS**。代价于是从 O(命中行) 变成 **O(语料)**。

### 4.3 已实测排除的七个替代解释

每一条都是跑出来的，不是推理掉的。这一节的意义在于：如果归因错了，下一轮会去优化一个
根本不是瓶颈的环节。

| # | 假设 | 实测 | 排除依据 |
| --- | --- | --- | --- |
| 1 | postings 列表太长 | 单元最大 DF **60**，CJK 单元 DF 1–2 | 没有长 postings |
| 2 | 命中行太多，bm25 打分贵 | MATCH 命中行 p50 **3** / max **140** | 3 行不需要 500ms |
| 3 | OR 单元太多（长中文 query 产 18 个） | 18 单元 OR 只要 **0.50ms** | 逐单元 0.02–0.21ms，合起来也快 |
| 4 | `ORDER BY fts.rank` 的 bm25 排序 | 去掉 ORDER BY **反而变慢**（717ms） | 排序不是原因，rank 反而是优化 |
| 5 | `SELECT o.*` 取列太多 | 只取 `o.id` 也是 **0.82ms** | 与取列无关 |
| 6 | WAL 未 checkpoint（播种 4,000 次写） | checkpoint 前 571ms → 后 546ms | **无变化**，不是 WAL |
| 7 | JS 侧 `extractFtsSearchUnits` | ×100 共 **1.3ms** | 不是 JS |

第 6 条是我一度写进注释的错误结论，实测否掉后已改正——留在这里是因为"看起来合理"的
归因如果不验证，就会变成下一轮的错误前提。

### 4.4 为什么历史读数没受影响

O(语料) 在 30 行语料上就是 30 行。本轮用同一份 30 条 gold 语料复跑，
**search p95 = 12.2ms**，与历史的 12.4–16.9ms 一致。

所以：历史全部延迟读数**都是有效的**，只是它们测不到这个缺陷。这也说明 2A–R2 那些
"p95 < 300ms ✅"的判定并没有说谎——在 30 条语料上它确实成立。

### 4.5 影响面与"本轮不修"的理由

`src/db/index.ts` 有 **12 处 `LIMIT ?`**。其中 line 1160 `ORDER BY fts.rank LIMIT ?`
是 FTS 检索主路径，确认受影响。其余多数按已建索引的列排序，是否同样翻转**未逐一验证**。

不在本轮修，三条理由：

1. **判据 §2 第 1 条**：3B 不改生产。裁决原话是"先只建设和冻结装置，不改生产策略"。
2. **会破坏历史可比性**：修完之后所有历史 p95 读数与新读数不再可比，而那些读数是 2A–R2
   七个 Gate 的证据之一。这需要一次显式的重新基线，不能夹带。
3. **修法不唯一**：拼字面量 / 改写成子查询 / 让 FTS 子查询先取 rowid 再 join，各有取舍
   （SQL 注入面、可读性、是否影响其他 11 处）。选哪种需要独立判据和反向测试。

**建议作为独立一轮，优先级高于 3C。** 理由：它是用户能直接感受到的（工作区一大就变慢），
而且随语料线性恶化——2,000 条已经 1.5s。

### 6.2 判据修订 B1（如实披露）

## 7. 已知限制

判据 §9 预先写下 5 条，本轮实测又加 4 条。全部列出，避免事后挑选着说。

1. **recall 差距是构造出来的。** 目标被刻意放在窗口外，"200 窗口召回不到"是设计的必然，
   不是发现。装置量化的是**幅度、代价与副作用**：幅度 35.8% → 80.0%，副作用 +0.24 条/query
   误召回，**向量路径**代价 7.2ms p95（2,000 条）。注意这里说的是向量路径那一段——
   完整 search 的延迟由 §4 的缺陷主导，与候选池无关（§2.3.2、§2.4）。
2. **填充语料是模板生成的英文**，词面与主题多样性低于真实语料，可能**低估**真实工作区的
   噪声压力——真实工作区里 2,000 条记录彼此主题相关，压力更高。
3. **30 条标注目标全部来自本项目历史语料**，与 fusion 集同源，不构成泛化证据。
4. **时间轴压缩到 33 小时**，与真实分布不同；90 天窗口的交互留给 3C。
5. **performance-scale 用随机向量**：高维随机单位向量的 cosine 集中在 0 附近，过 floor 的
   候选比真实语料少，所以 RRF 之后的工作量**偏低估**。向量路径的 fetch 一段不受影响
   （只取决于 blob 条数），cosine 一段的分支预测可能偏乐观。
6. **三档性能的语料性质不同，跨档总延迟不可比。** 2,000 档是真实文本（含 §4 缺陷的完整
   代价），10,000 / 50,000 档是极简文本（`perf record N`）。所以出现了 10,000 档总延迟
   （p50 424ms）低于 2,000 档（p50 549ms）这种反直觉读数——那是文本长度差异，不是规模效应。
   **可比的只有向量路径读数**，它只取决于向量条数。
7. **RSS 读数噪声大，不足以排除泄漏。** 50,000 档逐轮 RSS = `[420, 400, 489, 502]MB`，
   非单调（400 < 420），所以判据 §7 "不得单调上涨"这一条**成立**；但趋势向上，需要更长
   运行才能排除。另有反常：播种后 10,000 档 237MB > 50,000 档 228MB，说明采样点受 GC
   状态影响。峰值 502MB，起始 94MB。
8. **§2.2 的 empty 均值 3.56 不能与历史 1.00 比较**（已在 §2.2 说明）。
9. **填充语料的 outcome/action 配对是随机的**，个别条目语义不自洽（例：动作"switched to a
   themed attribute"配结果"frame drops fell from 12 per screen to 1"）。对向量与词面压力无
   影响，但它不是"读起来像真实记录"的语料。
