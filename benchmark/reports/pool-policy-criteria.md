## 0. 预登记强度：本轮不是盲选，必须先说清楚

## 1. 本轮要回答的问题

`semanticCandidatePool` 当前为 200：语义腿只给「FTS 命中 ∪ 最近 200 条」打分。3B 已量化其代价
（2,000 条装置，190 条 relevance）：

| 指标 | `pool-200` | `pool-full` |
| --- | ---: | ---: |
| 语义腿触达 gold | 68 / 190（35.8%） | 152 / 190（80.0%） |
| hit@5 | 36.8% | 65.8% |
| `phase2` 子集（全部 `ftsCount=0`，n=72） | 触达 0，hit@5 **0.0%** | 触达 43，hit@5 31.9% |
| empty-like 均值 / 最坏（n=86） | 3.56 / 10 | 3.80 / 10 |
| `semanticOnlyMax` / 跨 scope 泄漏 | 2 / 0 | 2 / 0 |

本轮要决定的是**生产默认取什么值**，以及取那个值需要哪些前置条件。

### 1.1 为什么这实质上是一个二元决策

必须先写清楚装置的分辨力，否则"有限扩大"会被当成一个可以测出来的折中：

3B 装置把 30 条标注目标全部放在时间轴**最老端**，1,970 条填充全部更新。按
`turn_stopped_at DESC` 取池，于是收益对池值是一个**步进函数**：

```text
pool ≤ 1970          → 触达 0 条目标（与 pool-200 完全相同）
pool = 1971          → 触达 1 条（最新的那条目标）
pool ≥ 2000 / ∞      → 触达 30 条
```

推论，**必须实测验证而不是声称**（§6 G-STEP）：任何 500 / 1000 这类"有限扩大"在本装置上
读数与 `pool-200` **逐位相同**，成本却更高。它们不是"折中方案"，是**在本装置上被结构性支配
的方案**。

因此：**本装置能区分 200 与全 scope，不能校准一个中间常数。** 真实工作区里相关旧记录散落在
时间轴各处，中间池值会拿到部分收益——本装置看不到那一面，这条限制登记在 §11。

### 1.2 有限大池与 ∞ 在召回上不可区分，只在成本上可区分

装置只有 2,000 条，所以 `pool=5000` / `pool=20000` / `pool=∞` 的召回读数**必然相同**。
它们的差别只出现在 10,000 / 50,000 两档的延迟与内存上。所以本轮用两套 instrument：

- **召回 / 误召回 instrument**：3B 冻结的 2,000 条 recall-scale 装置；
- **成本 instrument**：3B 冻结的 10,000 / 50,000 performance-scale 装置。

有限池 P 的召回等价于全 scope，**仅在语料 ≤ P 时成立**；这是构造上的事实，不是测量结论，
超过 P 之后按 §1.1 的机制重新出现截断。选中有限池必须在 README 写明这个上界。

## 4. 运行 arm 之前已确立的三个机制事实

三条都是**探针**，不是 arm 读数，全部先于本判据冻结，逐条留档以便 Codex 复算。

### 4.1 SQLite 绑定参数天花板 = 65,535，越界即静默降级

`getObservationEmbeddingsByIds()`（`src/db/index.ts:913`）按候选数展开
`IN (?,?,…)`，绑定参数数 = `ids.length + 2`（model + dimensions）。实测 Bun 1.2.20 /
SQLite 3.43.2：

```text
65,535 个参数 → OK
65,536 个参数 → FAIL "SQLite query expected 0 values, received 65536"   ← uint16 回绕
100,000 个参数 → FAIL "expected 34464 values"  （100000 − 65536 = 34464）
```

所以候选 id 超过 **65,533** 条时该查询抛错，而检索内核的 `catch` 会把它吞成
`onDegrade()` + FTS-only（`observation-search.ts:1030` 附近）。**用户看到的是语义召回悄悄
消失，而不是报错。**

后果写进判据：`pool=∞` 在 scope∩90 天窗口内记录数超过 65,533 时存在一道**能力悬崖**。
它今天不可达（因为池是 200），选 ∞ 就会把它变成可达路径，且 3C 若放宽时间窗会更近。
处置见 §9.1（分块取向量，作为**前置条件**而非顺带优化）。

### 4.2 池扩大只能新增"无 FTS 命中"的候选（结构界 S1）

`candidateIds = FTS 命中 ∪ bigram 命中 ∪ 最近 N 条`（`observation-search.ts:1006`）。
FTS 命中**与池无关**，恒在候选内；bigram 关闭。所以扩池新增的候选必然没有词面命中，
它进页只能带 `match_source: 'semantic'`，因而**受 `semanticOnlyLimit=2` 约束**。

结论：**扩池带来的新进页记录数 ≤ 2 / 请求，与池大小和语料规模无关。** 这把"噪声会不会随
规模增长"从外推变成结构界。它必须被机械验证（§6 G5），不能只作为论证。

### 4.3 扩池只会让既有候选的语义名次变差（结构界 S2）

`semanticRank` = 通过 floor 的候选按 score 降序的位次。新增候选只能增加"比我分高的条数"，
所以既有候选的语义名次**弱变差**，RRF 分**弱下降**；FTS 名次不变。

推论：位移（既有记录被挤出页面、或彼此换序）是可能的，且不受 cap 约束——cap 只约束**新进页
者**。所以必须逐条测位移（§6 G6），不能用"新进页 ≤2"代替。

### 4.4 现有 p99 是 60 样本下的 max

3B / 修复轮的性能口径是 20 条 query × (4−1) 轮 = 60 样本，`p99 === max` 三档全部成立
（50,000 档 259.27ms = max）。本轮要求每（规模 × 池）≥ **200** 个丢首轮后样本
（20 query × 11 轮），否则 p99 只是最坏单次。

## 6. 可行性门槛（逐条机械可判）

### 6.0 修订 B1（2026-08-05，**在 6 个召回 arm 全部跑完之后**，经裁定批准）

原 G5 / G6 / G-STEP 三条按字面失败。失败的原因不是产品行为，而是**本判据自身两节互相
矛盾**，必须如实登记：

- §4.2（S1）证明的是**新候选**没有词面证据，因此只能以 `semantic` 进页；
- §4.3（S2）在同一份文件里预测了**既有候选**的语义名次会弱变差、RRF 分弱下降，
  于是**页面成员会重排**；
- 原 G5 却把 S1 的结论写成覆盖「新**进页**者」。一条本来就是 FTS 候选、只是没挤进前 10 的
  记录，会在别人分数掉得更多时升上来——那正是 S2，判据自己预测过。原 G-STEP 的
  「逐位相同」犯的是同一个错：把"未被打分"（触达，池的直接作用）与"排名结果"
  （受 S2 影响）混为一谈。

实测（pool-full，276 条 query）：新进页 416 条 = `semantic` 388 + `hybrid` 22 + `fts` 6。
按原字面即 28 条违反；而这 **28/28 在 `pool-200` 时就已在 `ftsRank` 候选集内**，
无法归因 0 条，semantic 新进页超过 2 条的 query 数 0 条。

**修订时点与强度**：修订发生在**看完全部召回 arm 之后**，因此预登记强度低于 A0，
与 FTS 修复轮的 B1 同级。抵消它的三件事：修订由裁定作出而非我自行决定；修订内容是把门槛改成
**可机械复算**的正确形式（新增了「必须已是 FTS 候选」这条原判据没有的归因要求，以及 G6′
把"退化须归因"收紧成"gold 不得掉出 top-5 / 整页"这条绝对门槛）；以及三条都有独立的机械
验证（§8.4 的复算命令）。

正式表述必须是**「含一次结果后判据修订的实验，修订经裁定批准并已披露」**，
不得写成"全程未修改的预登记实验"。

## 7. 选择规则（在任何 arm 读数产生之前写死）

只在通过 §6 全部门槛的 arm 中，按顺序执行，第一条能区分即停止：

1. 最大化 `phase2`（72 条 `ftsCount=0`）的**语义腿触达率**——它区分"打过分没排上"与
   "从未被打分"，是本轮缺口的直接读数；
2. 最大化 `phase2` hit@5；
3. 最大化 `phase2` MRR；
4. 最大化 `fusion` hit@5；
5. 最大化 `fusion` MRR；
6. 全部并列时，选**池值更大**者。理由预先写明：按 §1.1，中间常数在本装置上零收益却更高
   成本，保留的是同一个"按 recency 截断、按 cosine 排序"的结构缺陷；只有成本门槛失败才有
   理由选更小的池。

失败分支，同样预先写死：

- **B-1**：`pool-full` 通过全部门槛 → 生产默认改为 `Number.POSITIVE_INFINITY`，
  且 §9.1 的分块取向量为**强制前置条件**；
- **B-2**：`pool-full` 仅因 G13–G17 中的成本门槛在某一档失败 → 选择**在全部已测规模上都
  通过全部门槛的最大有限池**，并在 README 登记该池值即召回等价上界（§1.2），同时把"超过该
  规模需要分块打分 / 分页扫描"登记为独立后续轮次；
- **B-3**：`pool-full` 因 G1–G12 中任一**质量或安全**门槛失败 → 不改默认，本轮结论为
  「保持 200」，并逐条给出失败归因。质量失败不得用"成本可接受"抵消；
- **B-4**：无任何 arm 在 G7 上优于基线 → 保持 200，结论为未通过。这是合法结论。

不得用 `heldout` / `validation` / Codex 审计集的读数打破任何并列。

## 11. 先写下来的已知限制

1. **本装置无法校准中间池值**（§1.1）。目标全在最老端，收益对池值是步进函数。真实工作区里
   中间池值会拿到部分收益，本轮不给出那条曲线。
2. **有限池的召回等价性是构造事实**（§1.2），仅在语料 ≤ 池值时成立，未测量。
3. **误召回只在 2,000 条真实向量语料上测过。** 10,000 / 50,000 档是随机向量，不能测相关性。
   规模上的安全性依据是 §4.2 的结构界 + G5 的机械验证，**不是**大规模误召回读数。
4. **"全 scope"今天等于"全 90 天窗口"。** days 未改（§2 第 5 条），装置又把时间轴压到 33
   小时以隔离窗口效应，因此本轮读数不含与 90 天窗口的交互——那是 3C。
5. **floor=0.197 是在 30 条语料上校准的。** 扩池不改变 cap 对**数量**的约束，但语义-only 那
   最多 2 条线索会从全 scope 里挑，其 cosine 更高、看起来更可信。这是噪声**质量**的变化，
   不是数量的变化，无法用本轮读数量化。
6. **端点读数已公开**（§0），本轮不是盲选。
7. **§6 部分门槛数值为非盲设定**（§6 末）。
8. **50,000 档 p99 余量小**：修复轮读数 259.27ms / 300ms 门槛，余量 14%，且那是 60 样本下的
   max。G14 改用 200 样本与 500ms 门槛后，结论可能与修复轮的表述不同——以本轮读数为准。

## 12. 修订 B2：性能门补证轮（裁定预先固定，冻结于任何补测运行之前）

> 裁定（2026-08-05）：本轮结论为**暂不通过，补证后重新验收**——不是"有条件通过"，
> 因为补测结果可能把生产策略从 `Infinity` 改成 `20000`，那会改变算法选择。
>
> **补测完成前，代码里的 `Infinity` 只是候选默认值，不得发布。**

### 12.1 为什么 10,000 条真实向量不能直接核销 50,000 条性能门

`perf-floor-worst`（floor=−1）测出 50,000 档 p95 **314.15ms**，超预算；发布 floor 下同档是
254.15ms。真实读数落在两者之间，位置取决于**过 floor 的比例**，而随机单位向量测不到这个比例。

10,000 条真实向量能确定的只是**真实 cosine 分布**，它本身不是 50,000 条的性能读数。所以补测
分两步，缺一步都不成立：

1. 用 10,000 条真实 `semantic-en-v1` 向量测出生产 query 下**过 0.197 floor 的比例分布**；
2. 把该向量分布**确定性回放**到 50,000 个候选上，再测完整 search。

不要求重新编码 50,000 条：允许把 10,000 条向量以**不同 Observation ID 重复 5 份**。
重复不改变 cosine 分布，因此过 floor 的比例逐位保留——这是回放成立的前提，也是它比
"随机向量 + 外推"强的地方。

### 12.2 装置规格

| 项 | 值 |
| --- | --- |
| 文本 | 10,000 条填充，**沿用 3B 冻结的生成规则与词面检查**（同一 `DOMAINS` 表、同一 78 独特 concept + 33 文件基名禁用表、标题唯一），只改 `count` |
| 向量 | 10,000 条真实 `semantic-en-v1`，生产模型 `all-MiniLM-L6-v2:q8:384`，同一 `buildObservationSearchText()` |
| 50,000 档 | 同 10,000 条向量重复 5 份，Observation ID 互不相同；第 k 份用 `filler[i % 10000]` 的文本与向量 |
| 冻结 | 文本与 checksum 落盘，写入报告 provenance；冻结后不得因读数回改 |
| query | 复用既有冻结 query 集与英文派生值，不新出题 |
| 样本 | 每（规模 × 池）≥ **200** 个丢首轮后样本 |

### 12.3 双进程口径（裁定要求，不可用单进程替代）

`perf-floor-worst` 的 1235MB 全局峰值里混着**播种 50,000 条**的代价，把它算给搜索是错的。
因此补测必须拆成两个进程：

```text
进程一：--phase=seed    建库、写向量、退出（峰值属于播种，与搜索无关）
进程二：--phase=measure 重新打开同一个库、只做检索、报告自己的 RSS
```

进程二的读数才是搜索的内存代价。

### 12.4 补测门槛（裁定预先固定）

| # | 门槛 | 阈值 |
| --- | --- | --- |
| P1 | 完整 search p95 @50,000（回放真实向量分布） | < 300ms |
| P2 | 完整 search p99 @50,000 | < 500ms |
| P3 | **检索进程**的循环内 RSS 增量 @50,000 | ≤ 512MB |
| P4 | **检索进程**的绝对峰值 RSS @50,000 | ≤ 1024MB |
| P5 | 丢首轮后样本数 | ≥ 200 |
| P6 | `degrade` 计数 | 0 |

### 12.5 分支（在补测运行之前写死）

- **P1–P6 全部通过** → 接受 **A**：生产使用 `Infinity`；
- **任一失败** → 本轮进入 **B-2**：生产使用 **20000**，并且必须明确写出「它在 50,000 条语料上
  截断 60%」，**不得宣称召回等价**。

内存门（P3/P4）任一失败即判 `Infinity` 不可行——与延迟门同等，不作权衡。

### 12.6 不追溯改写 G16

`floor=−1` 是预登记的**不参选**诊断 arm，所以 1235MB **不**事后改写成正式 G16 失败。
它的作用是暴露风险并触发本节的补测，而不是变成一条回溯判定。

### 12.7 盲审集为验收前置（不得验收后补）

现有确认集没有任何一份能验证"超过最近 200 条之后扩大候选池"的泛化效果：G0 与 Codex 2B 盲审集
的装置分别是 30 / 26 条，池在它们上面不可能起作用；`heldout` / `validation` 的端点读数在 3B
已公开。

因此由 **Codex** 在性能策略冻结后独立建立并冻结 ≥20 条 zero-FTS relevance + ≥20 条
hard-negative，相关目标必须位于最近 200 条之外，冻结 query / 英文派生值 / gold / checksum 之后
才运行 `pool=200` 与最终候选策略。**G7 / G8 / G10 / G5′ 任一失败，本轮不通过。**
Kiro 不构造这份集合。
