# FTS `LIMIT ?` 缺陷修复轮判据（预登记，冻结于任何审计与改动之前）

> 版本 A0。冻结 checksum 与时间见 §9。
>
> 上游：Phase 3B 验收裁决（`benchmark/reports/phase3b-submission.md` 顶部 §四）——
> 开独立缺陷修复轮次，只把 `src/db/index.ts:1160` 作为必修项，其余 11 处**先审计再决定**，
> 修复后重跑三档完整 search 延迟。
>
> 缺陷证据：`phase3b-submission.md` §4。同一条 SQL，`LIMIT 50` 字面量 0.93ms、
> `LIMIT ?` 绑定参数 1506.57ms，返回行数都是 50；计划从「FTS 驱动 + 按 rowid 取回」
> 翻转成「扫 scope 内 90 天全部 Observation + 逐行探 FTS + 临时 B 树排序」。

---

## 1. 本轮的唯一目标

把 FTS 检索主查询的代价从 **O(语料)** 恢复成 **O(命中行)**，且**不改变任何返回结果**。

本轮是**缺陷修复**，不是优化，也不是策略调整。判定标准因此是"行为逐条不变 + 延迟下降"，
不是"某个质量指标上升"。

## 2. 明确的非目标（禁止项）

以下任一项发生即判本轮污染：

1. 修改任何检索策略字段值，包括 **`semanticCandidatePool` 保持 200**（3B 裁决明确未批准改动）；
2. 改变任何 query 的返回结果——行集合、顺序、`match_source`、分数，全部必须逐条不变；
3. **机械批量改写 12 处 `LIMIT ?`**。裁决第 3 条明确：先审计，只处理有翻转证据的；
4. 改 FTS tokenizer、`FTS_MIN_UNIT_LEN`、`FTS_CJK_WINDOW`、embedding 模型、`semantic-en-v1`
   协议、MCP schema、90 天窗口；
5. 顺手"优化" FTS 的召回逻辑（例如改 `extractFtsSearchUnits` 的单元预算）。召回是策略，
   本轮只碰执行计划；
6. 为了让延迟数字好看而改变 `limit` 的语义（例如把内部 FTS limit 50 调小）。

## 3. 审计口径（裁决第 3 条）

对 `src/db/index.ts` 中**全部** `LIMIT ?` 出现处，在**规模语料**上逐处采集：

| 采集项 | 说明 |
| --- | --- |
| `EXPLAIN QUERY PLAN`（绑定参数形式） | 生产实际形式 |
| `EXPLAIN QUERY PLAN`（字面量形式） | 对照 |
| 两种形式的实测耗时 | 预热后取多次 |
| 计划是否**翻转** | 判定依据见下 |

**"翻转"的判定规则**（先写死，避免看到计划再解释）：

绑定参数形式相对字面量形式，出现以下**任一**特征即记为翻转：

- 驱动表（计划第一行）不同；
- 绑定参数形式出现 `USE TEMP B-TREE FOR ORDER BY` 而字面量形式没有；
- 绑定参数形式出现 `SCAN`（全扫）而字面量形式在同一张表上是 `SEARCH`（索引查找）。

**只有被判为翻转、且实测耗时差异超过 10 倍的查询才纳入修复范围。** 两个条件都要满足：
计划不同但耗时相当，说明这个差异对该查询无实际影响，改它属于无证据改动。

审计结果必须**逐处**落档，包括判为"无需修复"的那些及其读数。

## 4. 修法候选与选择规则（先写死）

四个候选，全部要求**语义不变**：

| # | 修法 | 机制 | 已知风险 |
| --- | --- | --- | --- |
| A | `limit` 以**整数校验后内联为字面量** | 让计划器在编译期看到 LIMIT | 字符串拼接进 SQL——必须有整数校验，否则是注入面 |
| B | `CROSS JOIN` 固定连接顺序 | SQLite 文档化机制：`CROSS JOIN` 禁止计划器重排 | 把计划写死，将来数据分布变化时无法自适应 |
| C | 子查询先取 FTS rowid 再 join | 显式表达"先 FTS 后过滤" | **可能改变语义**：LIMIT 在 scope/days 过滤之前生效会少召回，需专门验证 |
| D | `ANALYZE`（建 `sqlite_stat1`） | 给计划器真实的行数统计 | 需要在迁移或运行时维护统计；对新库无效 |

**选择规则**，按序执行，不得在看到结果后调整顺序：

1. 排除任何**改变返回结果**的候选（C 若实测改变语义即出局）；
2. 在语义不变的候选中，选**实测耗时最低**的；
3. 若耗时差异小于 2 倍，选**改动面积最小**的（改动面积 = 受影响的行数 + 引入的新概念数）；
4. 若仍相同，选**不引入字符串拼接**的（A 有注入面，其余没有）；
5. 若没有任何候选把耗时降到与字面量形式同一量级（< 2 倍），本轮结论为**未通过**，
   如实报告并保留缺陷。

可以组合（例如 B + D），但组合必须作为**独立候选**登记并单独测量，不得先单独测 B、
再"顺手"加 D 然后报告组合读数。

## 5. 行为不变门槛（必须实测，不接受声称）

> ### 修订 B1（2026-08-05，**看到结果之后**，由裁决批准）
>
> **这是一次事后修订，必须如实披露：它发生在跑完全部候选、看到 239 条行为回放结果之后。**
> 预登记强度因此下降，本轮不得表述为"全程未修改的预登记实验"。
>
> #### 为什么修
>
> 原 §5 要求"239 条逐条 `resultIds`（有序）与修复前逐条相同"。实测之后发现这个门槛建立在
> 一个**错误前提**上：它假设存在"既快又逐条不变"的修法。实际上当前 FTS 腿的返回本身就
> **不确定**，有两层：
>
> 1. bm25 rank 精确相等时顺序未定义（SQLite 不保证），今天的顺序是查询计划的副产物；
> 2. 命中数超过内部 limit 50 时，平局落在截断边界上，于是**保留哪 50 条**——即成员——
>    也不确定。
>
> 所以**任何**改变计划的修法都会扰动它。唯一"逐条不变"的候选是 `ANALYZE`，而它之所以
> 不变，恰恰因为计划一个字没改、耗时也没降。原 §5 筛出来的不是"安全的修法"，是"不修"。
>
> #### 裁决的理由（原文要点）
>
> - 只解释等分换序（选项 1）会**保留 limit 50 边界上的成员不确定性**；成员变化会进入 RRF
>   与语义融合，**可能真正改变最终召回**，不能只登记为已知限制；
> - 为维护一个建立在错误前提上的判据而保留已证实的严重缺陷（选项 3）不合理。
>
> #### 修订后的行为门槛
>
> > **非 bm25 精确平局记录的相对顺序和成员不得改变；精确平局组允许改为预先声明的确定
> > 顺序；全部质量、安全指标不得回退。**
>
> #### 随之确定的实现要求（裁决指定，非我选择）
>
> - 保留 `CROSS JOIN`；
> - 改为 `ORDER BY fts.rank, o.id ASC`；
> - `o.id` **只作技术性全序键**——不使用 recency、pin 或 semantic score，避免在缺陷修复轮
>   里引入新的排名策略；
> - 接受 `TEMP B-TREE` 与约 11% 的局部代价，**前提是最终规模性能仍达标**。
>
> #### 随之调整的测试要求（原 §7 的补充）
>
> 1. 构造**多个** bm25 精确等分记录，确认严格按 `id ASC` 排序；
> 2. 构造**超过 50 条且平局跨越截断边界**的记录，确认不同查询计划得到**相同的有序 50 条
>    成员**；
> 3. 原"不得出现 `TEMP B-TREE`"的断言需要调整——修订后它会出现；但**必须仍然保证 FTS 是
>    外层驱动**；
> 4. 把 `CROSS JOIN` 改回普通 `JOIN` 时，反向测试**仍应失败**。

| 项 | 要求 |
| --- | --- |
| 非平局记录的相对顺序与成员 | **不得改变**（B1 修订后的口径） |
| bm25 精确平局组 | 允许改为预先声明的确定顺序（`id ASC`） |
| 全部质量与安全指标 | **不得回退** |
| `bun test` | 全通过 |
| `bun run typecheck` | 干净 |
| 内部 FTS `limit` 语义 | 仍为 50；返回行数上界不变 |

对照基线用 `benchmark/reports/phase3a-r2/baseline.json`（冻结的 R2 baseline arm，
逐字段 = 当前生产策略）。这是 3B 已经用过的同一条口径。

## 6. 延迟重测口径（裁决第 4 条）

修复后重跑 3B 的三档，**完整 search p50/p95/p99**：

| 规模 | 3B 修复前 p95 | 本轮门槛 |
| ---: | ---: | --- |
| 2,000 | 1222.97ms | 报告，并与 300ms 门槛对比 |
| 10,000 | 629.30ms | 同上 |
| 50,000 | 5985.60ms | 同上 |

要求：

- 复用 **3B 冻结的装置**（`phase3b-filler.json` / meta，checksum 必须匹配），不新建语料——
  换语料就无法与修复前对比；
- 取样口径与 3B 一致：4 轮取分位数、丢首轮、首轮单独报告；
- 同时报告**分阶段**读数（embed / fts / fetch / cosine），证明下降来自 FTS 一段；
- 三档是否满足 300ms **如实报告**。本轮不预设它必须达标：若某档仍超限，说明还有第二个
  瓶颈，那是下一轮的对象，不是本轮失败。

## 7. 必须新增的测试

1. **反向测试**：构造一个能捕获计划翻转的断言。计划本身不稳定（依赖 SQLite 版本与统计），
   所以断言的是**可观测后果**而非计划文本——具体形式在实现时确定并在报告中说明理由；
2. **行为等价**：修复前后同一 fixture 上 FTS 返回的 id 与顺序相同；
3. **`limit` 边界**：`limit = 1 / 50 / 0`（若合法）行为正确；
4. 若选定修法 A：**整数校验的反向测试**——非整数 / 负数 / 超大值 / 字符串必须被拒绝，
   不得拼进 SQL；
5. 若选定修法 B：验证 `CROSS JOIN` 未改变结果集（只改计划）。

## 8. 通过判定

五项全部成立才算通过：

1. 全部 12 处 `LIMIT ?` 审计留档，翻转判定按 §3 规则机械执行；
2. 修复范围只含**有翻转证据且耗时差异 > 10 倍**的查询；未改的逐处说明理由；
3. 行为不变（§5 全部满足，239 条逐条 0 差异）；
4. 三档完整 search 延迟重测完成，与修复前逐档对比，下降归因到 FTS 一段；
5. `bun test` 全通过、`typecheck` 干净，新增测试覆盖 §7。

任一项缺失即未通过。**不得因为延迟下降明显就放松行为不变的要求**——一个改了返回结果的
"修复"是策略改动，需要走质量 Gate，不是缺陷修复。
