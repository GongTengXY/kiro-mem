### 2.1 审计脚本自带的转写校验抓到两次比对错误

脚本必须把生产动态拼出的 SQL 抄一份才能 EXPLAIN，抄错就会审计到一条生产从不执行的语句。
所以每处都带 `verify`：跑生产方法、跑转写 SQL，断言行 id 逐条相同。它当场抓到两次：

1. **L1160**：我最初拿**字面量形式**去比生产的**参数形式**，报"不一致"。追下去发现两种形式
   返回**相同的 49 行**，只在 bm25 平局处顺序不同——是比对口径错了，不是转写错了。
   这次误报直接引出了 §4 那个更重要的发现。
2. **L1393**：生产返回 `olderDesc.reverse()`（SQL 取 DESC 再翻成时间正序），转写的是 SQL
   本身，所以要把生产结果翻回去才是同一个东西。

两处都不是"改改断言让它过"，是比对定义本来就错。

## 3. 修法选择

判据 §4 登记了 A/B/C/D 与组合，并预写了选择规则。实测（1,970 条语料，5 次取中位数）：

| 候选 | 耗时 | 计划 | 行集合 | 顺序 |
| --- | ---: | --- | :--: | :--: |
| `current`（`LIMIT ?`） | 843.9ms | `SEARCH o` → `SCAN fts` → `TEMP B-TREE` | 基准 | 基准 |
| **A** 整数校验后内联字面量 | **0.544ms** | `SCAN fts` → `SEARCH o BY rowid` | 4/5 同 | 异 |
| **B** `CROSS JOIN` 固定连接顺序 | **0.522ms** | `SCAN fts` → `SEARCH o BY rowid` | 4/5 同 | 异 |
| C 子查询先取 FTS rowid | 0.823ms | `CO-ROUTINE` + `TEMP B-TREE` | 4/5 同 | 异 |
| **D** `ANALYZE` | **855.7ms** | 与 current **完全相同** | 5/5 同 | 同 |
| B+D 组合 | 0.548ms | 同 B | 4/5 同 | 异 |
| 诊断：字面量 + 显式 `(rank, o.id)` | 0.581ms | `SCAN fts` + `TEMP B-TREE` | 4/5 同 | 异 |

两条读数值得单独说：

- **D（`ANALYZE`）完全无效。** 建了 `sqlite_stat1` 之后计划**一个字没变**，耗时 855.7ms
  对 843.9ms（噪声内）。所以这不是"计划器缺统计信息"，而是"LIMIT 值在编译期不可知"——
  真实行数统计并不能补上那个信息。
- **C 比 current 快，但只快 1000 倍不到，且仍带 `TEMP B-TREE`。** 它把 LIMIT 放在
  scope/days 过滤之前，判据 §4 预先登记了"可能少召回"的风险；实测它在行为上与 A/B 同类，
  没有额外好处，成本却是一层子查询。

**选定 B（`CROSS JOIN`）**，已实现于 `src/db/index.ts:1176`。理由按判据 §4 规则 4：
B 与 A 速度相同（0.522 vs 0.544ms，2 倍内并列），而 **A 要把值拼进 SQL 字符串**，
需要整数校验才不成为注入面；B 把 `limit` 继续留作绑定参数，不引入那个面。

`CROSS JOIN` 是 SQLite 文档化的固定连接顺序机制，不是偏方。代价是把计划写死——但这里
只有一个合理顺序：FTS 先收窄到几十行，`observations` 随后是主键查找。

## 4. 修复过程中发现的第二件事：当前 FTS 返回本身不确定

这件事不是修复引入的，是修复**暴露**的，而且它决定了 §5 的裁定请求。

### 4.1 平局：顺序未定义

两种 LIMIT 形式返回**相同的行**，但在 bm25 rank **精确相等**处顺序不同。1,970 条语料上
一条 query 实测：8 个平局组、涉及 20/49 行；按 `(rank, id)` 归一化后两者**完全一致**。

SQLite 不保证 `ORDER BY` 在等值处的顺序。所以今天那个顺序是**查询计划的副产物**，
不是设计选择。

### 4.2 截断：命中超过 limit 时连成员都不确定

更要紧的一层。当命中行数**超过内部 limit 50** 时，平局落在截断边界上，于是"保留哪 50 条"
也取决于那个未定义的顺序。实测：5 条 query 里有 1 条正好返回 50 行，那一条的**行集合**
在两种形式下真的不同。

### 4.3 这件事在 gold 语料上的实际暴露面

30 条 gold 语料（所有历史读数都用它）实测：

| 项 | 读数 |
| --- | ---: |
| 有 FTS 命中的 query | 90 |
| **命中数达到 limit(50) 的** | **0** |
| 存在 rank 平局的 | 3（v15 / w17 / w33，各 1 组 2 行） |
| 两种形式行集合不同的 | **0** |
| 两种形式顺序不同的 | 3 |

所以在 gold 语料上，§4.2 那类**行成员不确定完全不会发生**（0 条达到 limit），
只剩 3 条 query 的平局顺序会变。

## 5. 需要裁定：判据 §5 与实测的冲突

### 5.1 实测的行为影响：239 条里只有 1 条

用 3B 同一条口径（对照冻结的 `phase3a-r2/baseline.json`）复跑 239 条：

```text
逐 query 差异: 1 / 239

w33 (relevance)
  旧: t15,t08,t14,t21,t07,t06,t22,t16,t01,t02
  新: t08,t15,t14,t07,t21,t06,t22,t16,t01,t02
  gold rank 旧=[9] 新=[9]
```

全部指标**逐位相同**：`hit@5` 0.875 / `MRR` 0.8493055555555558 / `R-precision` 0.825 /
tuned 1.0·0.9444 / fusion 0.8387·0.8217 / phase2 0.5 / empty-ext 1.875·10 /
expected-empty 1·2 / leakage 0。

### 5.2 这 1 条差异的完整归因

w33 的 FTS 排名里**只有一个平局组**，实测：

```text
  10. t07  -0.000001016125
  11. t15  -0.000001016125      ← rank 完全相同，且是全表唯一平局组
```

FTS 腿唯一能变的就是这一对的先后。返回页上出现两处互换（t15/t08、t21/t07），
是这一对 ftsRank 互换后经 RRF 传导的结果——**gold 答案仍在第 9 位**。

### 5.3 判据 §5 的冲突与它的收口

修复之前，判据条款与实测的关系是：

| 判据条款 | 字面要求 | 实测 |
| --- | --- | --- |
| §4 规则 1 | 排除任何**改变返回结果**的候选 | A/B/C/BD 全部改变 → 全部排除 |
| §4 规则 5 | 没有候选把耗时降到同量级 → **未通过** | 语义不变的只有 D，D 完全不提速 |
| §5（原） | 239 条逐条 `resultIds` 相同 | 238/239 |

按字面执行，结论会是"未通过、缺陷保留"。

判据在这里写错了对象：它假设"存在一个既快又逐条不变的修法"，而实际上**任何**改变计划的
修法都会扰动平局顺序，因为那个顺序从来没有被定义过。D 之所以"逐条不变"，恰恰因为它
**什么都没改**——计划一个字没变。所以 §4 规则 1 筛出来的不是"安全的修法"，是"不修"。

**裁决选择了选项 2**：修订门槛，**并且**把平局顺序确定化。裁决的关键论证是我当时没有充分
强调的一层——选项 1（只修订门槛、不动排序）会**保留 §4.2 那类成员不确定性**，而成员变化
会进入 RRF 与语义融合，**可能真正改变最终召回**，那不是可以登记为已知限制的东西。

修订后的门槛（判据 §5 B1）：

> 非 bm25 精确平局记录的相对顺序和成员不得改变；精确平局组允许改为预先声明的确定顺序；
> 全部质量、安全指标不得回退。

### 5.4 修订门槛的独立验证：0 条违反

门槛必须在**FTS 腿这一层**验证，因为那是本修复触碰的层；最终页的顺序由 RRF 融合三条腿产生，
任何输入名次变化都会级联，用最终页去验证会把级联误判成违反。

`benchmark/verify-fts-tie-gate.ts` 对全部 query 逐条比较三种形态——修复前（`JOIN` + `rank`）、
中间态（`CROSS JOIN` + `rank`）、当前（`CROSS JOIN` + `rank, id ASC`）——并机械检查三条：

```text
有 FTS 命中的 query 中，含 bm25 精确平局的: 3
违反 B1 修订门槛的 query: 0

  v15 平局组: t13(id13)=t07(id7)   →  当前次序 t07,t13
  w17 平局组: t15(id15)=t13(id13)  →  当前次序 t13,t15
  w33 平局组: t15(id15)=t07(id7)   →  当前次序 t07,t15
```

三条逐一成立：

| 门槛 | 检查方式 | 结果 |
| --- | --- | :--: |
| 成员不得改变 | 修复前与当前的行 id 集合 | 全部相同 |
| 非平局记录相对顺序不得改变 | 剔除平局组成员后的序列逐位比 | 全部相同 |
| 平局组按预先声明的确定顺序 | 组内次序须严格等于 `id ASC` | 3/3 成立 |

三个平局组的确定次序 t07<t13、t13<t15、t07<t15 都是 id 升序。

### 5.5 最终页的那一处变化如何与门槛相容

239 条回放里 w33 的返回页是：

```text
旧: t15,t08,t14,t21,t07,t06,t22,t16,t01,t02
新: t08,t15,t14,t07,t21,t06,t22,t16,t01,t02
成员相同: true      gold rank: 9 → 9
```

t08 与 t21 看起来"也动了"，但它们并没有与彼此换位——动的是平局对 (t07, t15) 的 ftsRank 互换
之后，这两条在 RRF 融合分上相对 t08 / t21 的位置发生了级联。w33 的 FTS 排名里**只有这一个
平局组**，所以级联的源头唯一且可证。

这正是 §5.4 必须在 FTS 腿层面验证的原因。

### 5.6 事后修订的诚实边界

B1 是一次**看到结果之后的判据修订**，判据文件与本节都已明确标注。本轮因此**不得**表述为
"全程未修改的预登记实验"，正确表述是**"含一次结果后修订的实验，修订经裁决批准并已披露"**。

（新增了"成员不得改变"这条原判据没有的要求）；以及门槛有独立的机械验证脚本（§5.4）。

### 7.1 新增测试与它们的判别力

| # | 测试 | 断言什么 |
| --- | --- | --- |
| 1 | 驱动表是 FTS 虚表 | 计划第一行含 `VIRTUAL TABLE`，不含 `idx_observations_scope_time` |
| 2 | `TEMP B-TREE` 出现是**预期的**，但 FTS 仍是外层驱动 | 计划含 `TEMP B-TREE`，第一行仍是虚表，且**不含 `SCAN o`** |
| 3 | `limit` 仍是绑定参数 | 源码含 `CROSS JOIN ...` 与 `ORDER BY fts.rank, o.id ASC LIMIT ?`，且**全文件不含 `LIMIT ${`** |
| 4 | 多个 bm25 精确等分 → 严格 `id ASC` | 8 条逐字相同文本 → rank 全等 → 返回顺序须恰为 id 升序（**B1 要求 1**） |
| 5 | 平局跨截断边界 → 不同计划相同的有序 50 条 | 60 条逐字相同 → 60 行平局组横跨 50 行边界；`CROSS JOIN` 与普通 `JOIN` 须**逐条相同**，且须是 id 最小的 50 条；生产方法走同一条路（**B1 要求 2**） |
| 6 | 行集合稳定 | 同一 fixture 上两次调用行集合相同 |

第 2 条是按裁决**调整**的：B1 之后 `ORDER BY fts.rank, o.id` 是复合键，FTS 模块能流式给出
自己的 rank 次序但给不出复合次序，所以 `TEMP B-TREE` 必然出现。断言因此从"没有排序"改成
"排序的存在不影响驱动方向"——1900 倍的收益来自谁做外层循环，不来自有没有排序。

第 5 条是本轮最强的一条：它直接测**成员**确定性，而且对照的是**两种查询计划**。修订之前
这两者在这个 fixture 上会给出不同的 50 条；修订之后必须逐条相同，那才是"成员不再取决于
计划"的实证。

#### 7.1.1 反向测试抓到我自己的测试设计缺陷，如实留档

`CROSS JOIN` 的 SQL 会有 `CROSS JOIN` 的计划"，同义反复，零判别力。

写"反向测试"而不是"新增测试"：没有它，这三条测试会以通过的样子躺在仓库里。

## 9. 已知限制

1. **`ANALYZE` 无效这条结论是在本语料上得的。** 计划一个字没变、耗时无变化，机制上
   （LIMIT 编译期不可知）也说得通，但没有在其他数据分布上验证。
2. **其余 11 处只在 1,970 条语料上审计过。** 判定依据是"计划无差异且比值 < 10×"，
   它们大多按已建索引的列排序，机制上不该随规模翻转，但**没有在 50,000 条上复核**。
3. **修复后的三档读数继承 3B 的语料性质限制**：2,000 档是真实文本，10,000 / 50,000 档是
   极简文本，跨档总延迟仍不可比（3B §7.6）。
4. **`phase3b-scale.json` 被本轮覆盖。** 3B 的修复前读数保留在 `phase3b-submission.md`
   的表格里，但那份机器可读 JSON 已经是修复后的。想要修复前的完整 JSON 需要
   `git stash` 本轮改动后重跑。
5. **50,000 档 p99 = 259.27ms，余量 14%。** 不是本轮引入的（不加平局键时 189.00ms，
   同档次运行间波动较大），但它是最接近 300ms 的读数，应作为候选池轮次的输入。
6. **平局的确定顺序是一个约定，不是相关性判断。** `id ASC` 意味着在排序器无法区分的记录
   之间，**较早写入的胜出**。这是一条明示的、任意的、稳定的约定；它没有声称旧记录更相关。
   若将来要让平局按别的键决出（recency / pin / semantic score），那是排名策略改动，
   需要独立的质量 Gate——本轮刻意没有那么做。
7. **B1 是结果后修订**（§5.6）。预登记强度低于 3A-R2 的 A2。
