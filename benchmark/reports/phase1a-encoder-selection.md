## 两处本轮修掉的探针方法论缺陷

都是我们自己的尺子出的问题，都会静默给出错误结论，所以记下来。

**一、绝对间距不能用来在候选之间排序。** 第一版画像探针把"改写对 − 无关对"当作横向
比较量，于是 e5-small 拿到几乎全 0.0x 的间距、看起来最差——而它的排名 MRR 恰恰最高。
原因是句向量模型的各向异性差别很大：E5 的全部 cosine 挤在 0.8+ 的窄带里，间距 0.06
已足够把顺序分开。已改为：绝对间距只作**模型内部**的方向性自检（看正负），横向比较
统一用标度无关的 **AUC**。

**二、候选 floor 的扫描区间不能写死。** 第一版按当前编码器的量级写死 0.20–0.70，对
e5-small 直接产出"零个候选"——它的工作点在 0.85 附近。那不是"这个模型没有可用工作
点"，而是尺子量程不对，且失败是静默的：表格照样生成，候选栏空着。已改为按两个分布的
联合跨度自适应。

这两条与 §9 纪律 2 是同一类错误（用一个结构上读不出变化的量当判据），只是发生在探针
自身的口径上而不是门槛上。

## 方案原估算的偏差

| 项 | §5.8 估算 | 实测 | 偏差 |
| --- | --- | --- | --- |
| 包体积（e5-small 运行文件） | 118 MB（查阅值待复测） | **129.1 MB** | 偏低 11 MB（HF 上 onnx 单文件 118.3 MB，另有 tokenizer 等） |
| 冷启动 | 268ms → 0.5–1s | 98ms → **462ms** | 量级正确 |
| 长文本延迟 | 42ms → 约 85ms | 36ms → **78ms** | 量级正确 |
| **RSS/进程** | 279MB → **约 400MB** | 178MB → **753MB** | **严重偏低**，见下 |

**RSS 这一项的偏差改变了成本判断。** 方案否掉 `bge-m3` 的核心理由之一是"每个 Kiro
会话的 MCP 进程各加载一份，估算 0.9–1.2GB/进程，三个会话约 3.5–4.8GB"。实测 e5-small
是 **753 MB/进程**，三个会话约 2.3GB——离被否掉的那条线远比方案假设的近。同一套否决
逻辑应当一致地施加到这里，而不是只用在 bge-m3 上。

## 跨语言对比（本轮补测，**它推翻了本报告的第一版推荐**）

第一版对比只有中文 query，所以"中文专用模型丢英文"在数据上测不出来，我把它列为
bge-small-zh 的阻塞项。现在它测出来了。

### 英文镜像的构造与举证能力

`benchmark/dataset/mirror-en.json`：把 26 条 primary 记录参与嵌入的字段
（title / summary / outcome / learned / concepts）与 18 条 tuned + 5 条 empty query
**机械 1:1 翻译**成英文。`expect` 标注、dataset id、scope、文件路径**一字不改**——
路径与标识符是语言中立的，翻译它们会让检索任务变成另一个任务。

必须说清它是什么：

- **它是校准集的派生物**（来自 `tuned` + `empty`），所以是校准证据，**永远不能**当
  泛化证据引用。`heldout` 没有镜像，也不该有。
- **翻译是我们自己写的**，所以绝对读数带译者偏差。但**相对比较仍然成立**：每个候选
  看的是同一份镜像，翻译质量对它们的影响相同。这与 §5.1 论证"`tuned` 可用于三候选
  相对比较"是同一条理由。
- 之所以做成机械镜像而不是现场手写几条英文 query：现在手写的任何 query 都是我**看过
  候选结果之后**选的证据（§9 纪律 5）。机械变换的规则可审阅，选择余地被消掉了。

三种语言配置各自对应一个真实产品场景：

| 模式 | 记录 | query | 对应场景 |
| --- | --- | --- | --- |
| `zh` | 中文 | 中文 | 中文用户（`language: zh`） |
| `en` | 英文 | 英文 | 英文用户。压缩产出的 Observation 语言跟随用户 prompt 语言，所以英文用户的**语料本身**也是英文——EN→EN 才是英文用户的真实场景，不是跨语言 |
| `cross` | 中文 | 英文 | 双语开发者（有时中文提问、有时英文提问，同一个 workspace），以及"记录里全是中文叙述 + 英文标识符"这个常态 |

### 结果（18 条 tuned，离线语义 MRR）

| 编码器 | zh→zh | en→en | en→zh（跨语言） | 最弱格 |
| --- | --- | --- | --- | --- |
| 基线 all-MiniLM-L6-v2 | **0.529** | **0.972** | 0.704 | zh 0.529 |
| **e5-small**（带前缀） | 0.907 | 0.963 | **0.886** | **cross 0.886** |
| paraphrase-mMiniLM-L12 | 0.825 | 0.858 | 0.758 | cross 0.758 |
| bge-small-zh-v1.5 | 0.905 | 0.853 | **0.510** | **cross 0.510** |

三条结论，都是实测：

**一、基线不是"坏"，是"只会英文"。** 它在 en→en 上拿到 0.972，是四者**最高**。同一个
模型、同一份语料结构、同一套拼接，换成中文就掉到 0.529。这比 phase0 的固定句对是更
干净的病因证据：§1.1 的"用错了语言"从推断变成了对照实验。

**二、bge-small-zh 的英文缺口是真的，而且跨语言直接塌掉。** en→en 0.853（比 e5 低
0.110，比基线低 0.119），en→zh **0.510**——四者最差，几乎等于基线在中文上的水平。
方案 §5.1 写的"丢英文会牺牲 files / concepts / 命令名这类高信号字段"是对的，只是
真实的损失点更靠前：它在**英文 query 侧**就已经不行了。

**三、e5-small 是唯一没有弱格的候选。** 0.907 / 0.963 / 0.886，三个场景都在 0.88 以上。
paraphrase-mMiniLM 在两个英文格上都比基线还差（0.858 / 0.758），加上它已经被反向门槛
拦下，可以出局了。

### 前缀协议：测不出净收益，但仍要正确实现

| e5-small | zh→zh | en→en | en→zh |
| --- | --- | --- | --- |
| 带 `query:`/`passage:` | 0.907 | **0.963** | 0.886 |
| 故意不加 | **0.917** | 0.935 | **0.903** |

三格互有胜负，差值全部在单条 query 的分辨力内（1/18 ≈ 0.056），三格加总 2.756 vs
2.755。**结论只能是"这套校准集测不出前缀的作用"，不能是"前缀没用"**——上游 model card
明确要求它，而我们的样本量本来就不足以否证。

所以它的定位是**合规与健壮性**事项，不是质量杠杆：按 §5.3 拆 `embedQuery` /
`embedDocument` 并加断言测试，理由是**失效静默**（能跑、有分数、就是不准），而不是
"加了会更准"。

## 结论：选定 e5-small（带前缀）

**这是对本报告第一版推荐的修正。** 第一版推荐 bge-small-zh，条件是"先补上英文侧证据"；
证据补完了，它不成立。

| | e5-small ✅ 选定 | bge-small-zh ❌ | paraphrase-mMiniLM ❌ |
| --- | --- | --- | --- |
| 阶段 1 门槛（§5.5.1） | 全过，退化 0 条 | 全过，退化 1 条 | **未过**（单条退化 6 > 5） |
| zh→zh / en→en / en→zh | 0.907 / 0.963 / **0.886** | 0.905 / 0.853 / **0.510** | 0.825 / 0.858 / 0.758 |
| AUC（zh） | 0.946 | 0.918 | 0.987 |
| 维度 | 384（不动 schema） | 512（要动 blob 断言） | 384 |
| 运行文件 | 129.1 MB | 23.3 MB | 129.1 MB |
| RSS / 进程 | 753 MB | 171 MB | 752 MB |
| 冷启动 | 462ms | 62ms | 435ms |

选它的理由只有一条，但足够：**它是唯一在三个真实场景里都没有弱格的候选。** bge-small-zh
以 1/5 的成本拿到几乎相同的中文质量，这个诱惑是真的，但它的 en→zh 0.510 意味着一个
"平时中文、偶尔英文提问"的开发者会直接搜不到自己的记忆——而这不是边缘场景，中文语料里
本来就混着大量英文标识符。

### 选它要一起付的两笔账（必须记账，不能当成本已解决）

1. **包体积 23 MB → 129 MB。** README 现在承诺"模型随包发布、install 无需联网"，这一条
   仍然成立，但 `npm i -g` 的体积变成 5.7 倍。这是用户可见的产品变化，需要在 1b 里同步
   改 README / `docs/i18n/README.zh.md` 的所有"~23 MB"表述。
2. **RSS 178 MB → 753 MB / 进程，而且是每个 Kiro 会话一份。** 三会话约 2.3GB。方案 §5.8
   估的是"约 400MB"，实测偏低近一倍；而方案否掉 `bge-m3` 的核心理由正是"三个会话
   3.5–4.8GB"。同一套逻辑一致施加的结论是：**§10 的"向量计算集中到 Worker"从备选升级为
   1b 的必做项**，否则我们在用被否掉的那条线的量级去换质量。集中到 Worker 后这 753 MB
   只付一次（常驻热态），MCP 侧通过本地 HTTP 取向量，Worker 不可用时走已有的降级路径。

### 待复议候选

`paraphrase-mMiniLM-L12` 记为出局，不再复议：它不仅被反向门槛拦下，跨语言补测还显示它
在两个英文格上都比现有基线更差。它此前唯一的优势（AUC 0.987、误召回工作点最好）是中文
单格上的读数。

### 两个直接决定后续阶段的读数

**一、q38 的语义名次 11 → 1，所以 §5.5 的预测可以收口了。**

§4.6 已经把 q38 的 miss 归因为语义召回失败（期望记录不在 FTS 候选集里、语义第 11 位），
并指出修好它需要"语义 rank 11 → 前 3"。e5-small 把它放到了第 1 位。因此 1b 的端到端
预测是明确的：**heldout hit@5 = 50.0%（9/18），正好触到词汇锚点门还在时的理论上限。**
低于它说明 1b 实施出了问题，高于它不可能——那 9 条零锚点 query 结构上仍然返回空。

**二、9 条零锚点 query 的 Top-5 从 1/9 → 7/9，阶段 2 的收益第一次被量化。**

这 9 条今天返回空，不是因为排序差，而是因为词汇锚点门在语义步骤之前。它们的语义名次：

| query | 基线 | e5-small |
| --- | --- | --- |
| q28 | 1 | 1 |
| q40 | 21 | **1** |
| q42 | 21 | **1** |
| q30 | 8 | **1** |
| q32 | 14 | **2** |
| q36 | 24 | **3** |
| q29 | 10 | **4** |
| q37 | 19 | 11 |
| q33 | 24 | 13 |

**这给 §6.3 的 semantic-only 限额补了一个反向约束。** §4.6 已经证明 3 不能往下调
（q39 恰在边界）。现在多一条：拆门之后，7 条进入 Top-5 的零锚点 query 里有 6 条的语义
名次 ≤ 3（1/1/1/2/3/1），会被 `min(3, limit)` 保住；但 **q29 在第 4 位，会被限额切掉**。
