>

> ## 结论：**分支 B-2，生产使用 20,000**
>
> 质量上全 scope（`Infinity`）胜出，§7 的预登记规则也确实选中了它：那 72 条零关键词校准 query
> 从**结构上不可达**（语义腿触达 0/72）变成 43/72（hit@5 0% → 31.9%）；整体语义触达
> 35.8% → 80.0%，hit@5 36.8% → 65.8%，**没有任何一条 gold 掉出 top-5 或掉出整页**。
>

> 检索循环 RSS **+720MB > 512MB**（延迟反而通过：p95 277.35ms / p99 434.00ms）。
> 按裁定 §12.5 预先写死的分支，本轮进入 **B-2 → 20,000**，它在同一口径下六门全过
> （p95 183.15ms / p99 300.24ms / +384MB）。
>
> **20,000 不等价于全 scope**：超过 20,000 条的 scope 会重新按 recency 截断，50,000 条时
> 有 60% 从未被打分，而那部分召回损失**未测**（召回装置只有 2,000 条）。本报告任何地方
> 都不宣称召回等价。
>
> 本轮含 **B1**（结果后判据修订，经裁定批准，§5）与 **B2**（裁定预先固定的补证门，§12）。
> 正式表述必须是「含一次结果后判据修订的实验」。
>
> **仍缺一项验收前置**：判据 §12.7 要求的 Codex 盲审集尚未建立，须针对**最终策略 pool=20000**
> 构造。在它通过之前本轮不成立。

## 4. 运行 arm 之前发现的悬崖：65,535 个绑定参数

这是本轮最重要的**前置**发现，已写入判据 §4.1（先于 A0 冻结），也是选 ∞ 必须先修的东西。

`getObservationEmbeddingsByIds` 按候选数展开 `IN (?,?,…)`，绑定参数 = `ids + 2`。
实测 Bun 1.2.20 / SQLite 3.43.2：

```text
65,535 个参数 → OK
65,536 个参数 → FAIL "SQLite query expected 0 values, received 65536"   ← uint16 回绕
100,000 个参数 → FAIL "expected 34464 values"（100000 − 65536 = 34464）
```

于是候选 id 超过 **65,533** 时该查询抛错，而检索内核的 `catch` 把它吞成 `onDegrade()` +
FTS-only：**用户看到的是语义召回悄悄消失，不是报错**。池是 200 时这条路不可达；
选 ∞ 就把它变成可达路径，而 3C 若放宽 90 天窗会离它更近。

处置：本轮曾改为按 8,192 分块，**后按裁定回滚**（§2.1 与 §12.1 第 11 项）——最终选的是 20000，
候选数 ≤ 20,050 < 65,533，悬崖不可达，因此判据 §9.1「若最终未选 ∞ 则不落地」按原文执行。
留下的是一条底层测试：单条 `IN` 在 65,536 个参数处回绕失败、65,535 成功。它记录的是**天花板
的位置**，与是否分块无关——生产今天到不了，但失败模式是静默的（内核 catch → FTS-only），
所以未来抬池之前必须知道这条线在哪。

## 5. 判据修订 B1（结果后修订，经裁定批准）

### 5.1 冲突

原 G5 写的是「`results(arm) \ results(pool-200)` 中每条 `match_source` 100% 为 `semantic`」，
实测 pool-full 有 **28 条不是**（22 `hybrid` + 6 `fts`）。原 G-STEP 写的是「中间池 relevance
读数与 pool-200 **逐位相同**」，实测触达数恒为 68 但 hit@5 在 1970 是 37.4%。

### 5.2 根因是判据自相矛盾，不是产品行为

- 判据 §4.2（S1）证明的是**新候选**没有词面证据，因此只能以 `semantic` 进页；
- 判据 §4.3（S2）在同一份文件里预测了**既有候选**的语义名次会弱变差、RRF 分弱下降，
  于是**页面成员会重排**；
- 原 G5 把 S1 的结论写成覆盖「新**进页**者」。一条本来就是 FTS 候选、只是没挤进前 10 的记录，
  会在别人分数掉得更多时升上来——那正是 S2。原 G-STEP 犯的是同一个错：把"未被打分"
  （触达，池的直接作用）与"排名结果"（受 S2 影响）混为一谈。

### 5.3 修订后的门槛与机械验证

| 门槛 | 修订后内容 | 实测 |
| --- | --- | --- |
| G5′ | 新进页者必须满足二者之一：(a) `semantic` 且该 query 的 semantic 新进页数 ≤ cap；(b) 该 id 在 `pool-200` 的 `ftsRank` 候选集内 | pool-full：非 semantic 28 条，**28/28 命中 (b)**；**无法归因 0 条**；semantic 新进页 > 2 的 query 数 **0** |
| G6′ | 任何 arm 不得让 gold 掉出 top-5 或掉出整页 | 全部 arm **0 / 0** |
| G-STEP′ | 中间池的**触达数**与 pool-200 相同；`pool-1971` 恰好多触达 1 条目标 | 触达 200=500=1000=1970=**68**；1971 新触达目标恰好 **1 条（t26）**，翻转 query z29/z53/z54，可比向量 1964 → 1965，反向翻转 0 |

### 5.4 修订强度与一处脚本 bug 的如实登记

修订发生在**看完全部召回 arm 之后**，预登记强度低于 A0，与 FTS 修复轮的 B1 同级。抵消它的三件事：
修订由裁定作出而非我自行决定；内容是把门槛改成**可机械复算**的正确形式（G5′ 新增了原判据
没有的「必须已是 FTS 候选」归因要求，G6′ 把"退化须归因"收紧成绝对门槛）；三条都有独立验证脚本。

另需登记：`select-pool-arm.ts` 第一版把 G-STEP′ 的"多触达 1 条目标"实现成「两个 arm 各自触达
目标并集的大小之差」，两边都是 27，检查失败。那是**度量写错**不是门槛错——`t26` 在 1970 档
已被另一条有 FTS 命中的 query 触达过，所以并集不动。改成按 query 触达翻转归因后成立。
**门槛文本没有因为这次而变**。

## 6. 成本读数（200 样本/档，判据 §4.4 要求的口径）

| 规模 | pool-200 p95/p99 | pool-5000 | pool-20000 | **pool-full** | 300ms |
| ---: | ---: | ---: | ---: | ---: | :--: |
| 2,000（真实文本） | 8.11 / 10.77ms | 17.11 / 27.76 | 15.85 / 27.32 | **16.24 / 37.39** | ✅ |
| 10,000（极简文本） | 20.08 / 41.70 | 28.17 / 56.33 | 40.67 / 55.56 | **39.50 / 67.71** | ✅ |
| 50,000（极简文本） | 67.96 / 139.17 | 80.13 / 139.37 | 148.47 / 203.61 | **254.15 / 306.99** | ✅（余量 15%） |

`degrade` 全部为 0（G4），每档每池 200 个丢首轮后样本（G14）。

**必须与修复轮的读数对齐读法**：修复轮报的 50,000 档 pool-full p95 是 147.15ms，本轮是
254.15ms。差别不是回退，是**采样口径**——修复轮是 4 轮 60 样本（`p99 === max`），本轮是

其中 955MB 出现在 pool-200 那一轮，是**播种 50,000 条**的峰值而不是检索的——这正是本轮
把 RSS 归因到循环内的原因）；跨轮不单调上涨（G17 ✅）。

### 6.1 诊断 arm `perf-floor-worst`：floor 之后那一段的上界，**已超预算**

判据 §5.3 登记的诊断 arm（50,000 档、pool=∞、**floor = −1**，让全部 50,000 条通过 floor，
测出"打分后建数组 + 排序"这一段的上界，而不是外推）：

| 50,000 档 pool=full | p50 | p95 | p99 | 循环内 RSS | 全局峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| floor = 0.197（发布值，随机向量下几乎无人过 floor） | 120.98 / 135.46ms | **254.15ms** | 306.99ms | +444MB | 766MB |
| floor = −1（全部通过，**诊断**） | 241.16ms | **314.15ms** | 424.57ms | +361MB | 1235MB |

**这是本轮最重要的负面读数。** 两个端点都是实测的：真实 50,000 条语料的 p95 落在
**[254, 314]ms** 之间，取决于有多少候选过 floor——而真实向量的 cosine 分布比随机单位向量高，
过 floor 的比例更大。也就是说：**300ms 预算在 50,000 条上不是稳稳达标，而是在边界上。**

这不改变本轮的选择结果，理由是预登记的：诊断 arm 明确不参选（§5.3），而 G13/G14 是在登记的
instrument 上判定的。但它把"规模上限"从我原先写的约 60,000 条**收紧到 50,000 条附近，
并且在密集语料上可能更低**。README 已按这个口径改写，不是按 60,000。

**这一条已由裁定收口**：走补证路线 C，并把口径修正为「真实 cosine 分布 + 确定性回放 +
双进程内存」。补证结果见 §9：真实分布下 p95 是 **277.35ms**，落在 254（稀疏）与 314（全通过）
之间，与实测 9.2% 的过 floor 比例一致——**延迟门通过**。挡住 `Infinity` 的是内存门
（循环内 +720MB > 512MB），所以最终分支是 B-2。

## 7. 选择过程（`benchmark/select-pool-arm.ts`，机械执行）

```text
可行 arm：pool-200 / pool-5000 / pool-20000 / pool-full
淘汰：pool-500、pool-1000（G7 净收益 0，且未进入成本 instrument）
     pool-1970、pool-1971（判据 §5.1 登记为结构验证 arm，不参选）

规则 1 phase2 触达数：最优 43 → pool-5000, pool-20000, pool-full
规则 2 phase2 hit@5：31.9 → 三者并列
规则 3 phase2 MRR：0.306 → 三者并列
规则 4 fusion hit@5：80.6 → 三者并列
规则 5 fusion MRR：0.751 → 三者并列
规则 6 池值更大者 → pool-full
分支 B-1：默认改为 Infinity，分块取向量为强制前置条件
```

`pool-5000` / `pool-20000` 的召回读数**不是实测**，是构造上等于 `pool-full`（装置只有 2,000 条，
任何 ≥2000 的池覆盖全部语料）。脚本显式标注 `recallSource: 'by-construction'`，不把
`pool-full` 的数字当成它们的实测值。

§7 的规则选出 `pool-full`，理由是中间常数保留的是同一个「按 recency 截断、按 cosine 排序」的
结构缺陷。**但裁定追加的补证门（§9）推翻了这个落点**：`Infinity` 内存门失败，最终分支 B-2。

于是那处张力变成了已发布的事实——`pool=20000` 在 50,000 条语料上截掉 60%，**其召回损失
本装置测不到**（装置只有 2,000 条，任何 ≥2,000 的池读数相同）。这一条写进了 README、策略注释
与 §11 限制，**任何地方都不宣称召回等价**。

### 9.2 真实过 floor 比例：均值 9.2%，不是 100%

`perf-floor-worst` 用 floor=−1 测的是**上界**（100% 通过）。真实分布实测：

| ---: | ---: | ---: |
| 10,000 | **9.2%** / 0.4% / 28.0% / 29.7% | 924 / 2,966 |

分布本身也说明为什么 floor=−1 那个 314ms 是上界而不是估计——真实语料只有约 9% 过 floor。

### 9.3 双进程口径下的 P1–P6

进程一播种后退出（10,000 档峰值 338MB、50,000 档 221MB，**不计入搜索预算**），
进程二重新打开同一个库、只做检索并报告自己的 RSS。**每个池一个独立进程**——同一进程里
连测两个池会让第二个池的"循环前 RSS"继承前一个池的堆。

| 门 | 阈值 | `pool=Infinity` | `pool=20000` |
| --- | --- | ---: | ---: |
| P1 完整 search p95 @50,000 | < 300ms | ✅ **277.35ms** | ✅ **183.15ms** |
| P2 完整 search p99 @50,000 | < 500ms | ✅ 434.00ms | ✅ 300.24ms |
| P3 检索循环 RSS 增量 | ≤ 512MB | ❌ **+720MB** | ✅ +384MB |
| P4 检索进程绝对峰值 | ≤ 1024MB | ✅ 848MB | ✅ 467MB |
| P5 丢首轮后样本 | ≥ 200 | ✅ 200 | ✅ 200 |
| P6 degrade | 0 | ✅ 0 | ✅ 0 |

p50：151.86ms（∞）/ 88.85ms（20000）。

**延迟这一侧 `Infinity` 其实过了**——277.35ms 落在 254（稀疏）与 314（全通过）之间，
与 §12.2 的 9.2% 一致。挡住它的是内存。

#### 9.3.1 最终代码（**未分块**）的 pool=20000 确认

上表那次 `pool=20000` 测的是**分块实现**。裁定要求用最终代码重跑，所以下表才是发布形态的读数；
P3 是 GC 驱动的指标，因此跑三次留方差，不取一次：

| run | p50 | p95 | p99 | 循环内 RSS 增量 | 检索进程峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1（判定用） | 90.46ms | **183.39ms** | 342.72ms | **+461MB** | 547MB |
| 2 | 87.99ms | 121.86ms | 302.03ms | +466MB | 593MB |
| 3 | 89.95ms | 169.56ms | 282.64ms | +465MB | 592MB |

P1–P6 三次全过。**RSS 增量三次 461 / 466 / 465MB，跨度 5MB**——这个读数可复现，不是噪声；
它也反过来支持 `Infinity` 那次 +720MB 同样是真实工作集。

诚实登记两处相对分块实现的变化：P3 余量从 25%（384/512）降到约 **10%**（464/512）；
p99 从 300.24ms 变成 282–343ms 区间。前者可能来自实现差异（单条 20,000 参数查询一次性构造
SQL 与结果数组），也可能是 GC 方差，本轮不区分；后者三次都在 500ms 预算内。
判定采用 run 1，与其余两次同向。

### 9.4 那 720MB 是什么，以及为什么不是噪声

逐轮 RSS `[657, 690, 751, 825, 812, 729, 763, 718, 698, 759, 731]`——**振荡而非单调上涨**，
所以不是泄漏，是稳态工作集。机制可算：50,000 个候选要一次性取回 50,000 个 blob 行对象，
再逐行转成 `Float32Array`（50,000 × 384 × 4B ≈ 77MB 仅向量本体），加上平均 4,618 / 最坏
14,830 条过 floor 候选的打分数组。分块 fetch（本轮已回滚）只能解决 SQLite 的绑定参数上限，
**改不了**"全部聚合到内存再排序"这一点——这正是它不能充当规模修复的原因。

裁定已指出正确的修法：**分块读取 → 立即打分 → 只保留有界 Top-K**。那是独立一轮。

### 9.5 分支判定（脚本计算，不是散文）

`benchmark/select-pool-arm.ts` 现在同时复算 §7 规则与 §12 的 P1–P6：

```text

P1–P6：pool=full ❌（P3 +720MB）  pool=20000 ✅（六门全过）

```

`pool=20000` 作为退路本身也过了同一组门——否则 B-2 不成立，脚本会报"须上报"。

## 11. 已知限制

1. **本装置无法校准中间池值**：目标全在最老端，收益对池值是步进函数。真实工作区里相关旧记录
   散落在时间轴各处，中间池会拿到部分收益，本轮不给出那条曲线。
2. **有限池的召回等价性是构造事实**，仅在语料 ≤ 池值时成立（§7 的张力）。
3. **误召回只在 2,000 条真实向量语料上测过。** 10,000 / 50,000 档是随机向量，测不了相关性。
   规模上的安全依据是 S1 结构界 + G5′ 的机械验证（新候选只能以 semantic 进页且受 cap 约束），
   **不是**大规模误召回读数。
4. **随机向量低估了 floor 之后的排序工作量**（3B 已知限制 5）。判据 §5.3 的
   `perf-floor-worst` 诊断 arm 已运行并测到上界：50,000 档 p95 **314.15ms，已超 300ms 预算**
   （§6.1）。真实语料的读数落在 [254, 314]ms 之间，具体位置取决于过 floor 的比例，**未测**。
5. **"全 scope"今天等于"全 90 天窗口"。** days 未改，装置又把时间轴压到 33 小时以隔离窗口
   效应，所以本轮读数不含与 90 天窗口的交互——那是 3C。
6. **floor=0.197 是在 30 条语料上校准的。** 扩池不改变 cap 对条数的约束，但那最多 2 条
   semantic-only 线索现在从全 scope 里挑，cosine 更高、看起来更可信。这是噪声**质量**的变化，
   本轮读数无法量化。
7. **20,000 不等价于全 scope，超出部分的召回损失未测**：50,000 条 scope 里 60% 从未被打分。
   召回装置只有 2,000 条，任何 ≥2,000 的池在它上面读数相同——这条限制无法用本轮数据消除。
8. **内存才是规模瓶颈，不是延迟**：`Infinity` 在 50,000 条真实分布下 p95 277.35ms（预算内），
   却要 +720MB 工作内存（超 512MB 预算）。分块 fetch（已回滚）只解决 SQLite 绑定参数上限，
   **改不了**"全部聚合到内存再排序"。正确修法是分块读取 → 立即打分 → 有界 Top-K，属独立一轮。
9. **50,000 档的文本是 10,000 条重复 5 份**（裁定允许）。cosine 分布逐位保留（§9.2 两档比例
   完全相同），但 FTS 侧的命中形状与 50,000 条各自独立的语料不同，`[copy k]` 后缀只保证文本
   不逐字相同。
8. **端点读数已在 3B 公开**，本轮不是盲选；heldout / validation 对本轮不是干净确认集。
9. **B1 是结果后修订**（§5.4）。
10. **`run-phase3a-grid.ts` 有一处先于本轮的守卫失败**（§2.3），未修。
