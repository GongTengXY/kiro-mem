## 1. 四项裁决（含复审的收紧）

### 1.1 `commit` 类 `fact_source`：按事实性质要求，不设配额

**规则**：凡是「某行为**曾经存在、后来被删除或替换**」的事实，**必须**用对应 commit 佐证；
描述**当前状态**的事实可以由代码或报告支持。

明确不做的事：

- 不要求每批同时出现 `report` / `code` / `commit` 三种；
- **不为了凑数硬造 commit 记录**（原建议里"至少几条用 commit"这个说法作废，它是配额思维）。

冻结记录里登记来源版本与 SHA。

对本轮的直接影响：`c06`/`s06`（默认时间窗 90 天 → 无界）这类事实**必须**补 commit 来源——
"四处 `?? 90` 兜底曾经存在"是一个已被删除的行为，当前代码里查不到它，只能由 commit 佐证。

### 1.2 `age_days`：固定种子 + 固定脚本，Spearman 只作检查记录

- 用**固定种子**和**固定脚本**独立打乱年龄与插入顺序；
- 报告**年龄 vs 文本长度**、**年龄 vs 插入顺序**的 **Spearman** 相关系数；
- **相关系数只作检查记录**：不得临时设一个阈值、不得看到结果后重新洗牌。
  这一条是硬纪律——"洗到好看为止"等于用结果反向选装置；
- 种子、脚本 SHA、最终排列全部进入数据冻结记录。

原建议说的是"相关系数"，这里明确为 **Spearman**（秩相关），因为年龄与长度都不必是线性关系。

### 1.3 重建字段保持简短

`prompt` / `assistant_response` / `events` 只满足 fixture 结构，**不得刻意补成像真实对话的
长记录**。冻结记录必须明确写出：它们是重建字段，不参与 Observation、不参与向量、不参与 FTS，
也不用于 ACP 质量评估。

### 1.4 多 gold 默认检查：`related` ≠ `acceptable_gold`

- **`related` 不等于自动进入 `acceptable_gold`。** 必须针对**每一条 query** 单独判断
  "这条记录能不能回答这个具体问题"；
- 检查范围包括**新 40 条与旧 26 条**；
- **每条新记录至少要在一个 query 中作为 `primary_gold`。**

最后一条是新增的覆盖率要求（判据 §3 没写）。它把"40 条记录"从一个数量指标变成了可验证的
覆盖指标：一条从未当过 `primary_gold` 的新记录，对本轮的目的没有贡献。这条**收紧**了判据，
因此不构成对判据的放宽。

## 2. 第 4 步的执行解释：候选产出，冻结延后

### 2.1 判据 §7 的顺序缺陷（复审指出）

判据 §7 的步表是：

```text
4  扩到 40 条记录 + 110 条 query，生成并冻结英文派生值   ← 冻结
5  硬重复检查 + > 0.450 人工复核                        ← 可能删记录、改 acceptable_gold
```

这与判据 §5.1 第 1 层"重复项只保留一份"直接冲突：复核可能删除记录、改变
`acceptable_gold`，那第 4 步的冻结物就被改了——一个被修改过的冻结物不是冻结物。

pilot（第 2 步）已经实测：作者主动避让的前提下仍有 **2/5** 条撞上旧 gold。
所以"先冻结再复核"不是一个低概率风险，而是必然要触发的路径。

### 2.2 采纳的执行顺序

```text
1  产出 40 条记录候选                      不冻结
2  硬重复检查 + 全量 > 0.450 复核           逐对穷举，按 fact_source 裁决
3  确认最终 40 条记录及其 fact_source        删/换在这一步完成
4  写 relevance / hard-negative / 英文派生值
5  低分正例的「只增不删」程序（判据 §7.2）
6  一次性冻结数据与 query                   此后才能跑 P3 的第一个 arm
```

### 2.3 这个调整为什么不是对判据的放宽

| 判据里的禁止项 | 新顺序下是否仍然成立 |
| --- | --- |
| §5.1 第 3 层：不启用余弦自动删除 | ✅ 不变，复核仍只是筛查 + 人工裁决 |
| §5.4：0.450 复核带与"不启用自动删除"已冻结 | ✅ 不变，带子仍是 0.450 |
| §8.4：不得据语义 rank / cosine / 检索返回增删 query | ✅ 不变。复核动的是**记录**，依据是 `fact_source`；`§7.2` 的只增不删程序照旧 |
| §8.6：看过 arm 读数后不得改判据 | ✅ 不变，本文在任何 arm 之前落盘，且判据未被修改 |
| "第 4 步冻结完成前不得跑 P3 的任何 arm" | ✅ **更强**：冻结点后移，因此"第一个 arm 之前必须冻结"这条约束覆盖的范围反而变大了 |
| §10：英文派生值必须在第一个 arm 之前一次性生成并冻结 | ✅ 不变，仍在第 6 步之前生成 |

唯一变化是**冻结点从"记录落盘后"后移到"复核完成后"**。它使冻结物在冻结那一刻就是终态，
不再需要事后修补。方向上是收紧。

### 2.4 数量口径

**40 条记录 / 110 条 query 是数量下限，不是精确值。** 低分正例的补写程序（判据 §7.2）
可能让 relevance 超过 40 条。冻结记录填**实际数量**，不得为了对上"110"这个数字而删 query
——删 query 会直接违反 §7.2 的只增不删。
